# Дорожная карта реализации: Голосовой Generative UI («Сайт Будущего»)

Документ составлен строго на основе исследования «Архитектура Сайта Будущего: Голосовой Generative UI, Аудит Кодовой Базы Pipecat и Стратегия Монетизации для LabUpgrade.ai».

## Архитектурные принципы
1. **Неприкосновенность Legacy:** Существующий GSM + Telegram контур (`/ws` + `RawPCMFrameSerializer`) не переписывается и не нагружается условными ветвлениями.
2. **Модульная декомпозиция (Shared Core):** 95% общей логики выносится в пакет `core/` (Supabase, микшер, вебхуки n8n, пост-обработка Архивариуса).
3. **Изолированный транспорт:** Новый контур для «Сайта Будущего» строится в отдельной точке входа на базе WebRTC (`SmallWebRTCTransport` / `aiortc`), `RTVIProcessor` и `UIWorker`.
4. **Фокус на B2B / B2B2C:** Полный отказ от B2C-расширений в пользу двухуровневой B2B-модели (кастомный сайт под ключ + встраиваемый SaaS Co-Browsing SDK).
5. **Чистый бэкенд:** Реализация охватывает только серверную архитектуру, протоколы, тулы и API-контракты (без фронтенд-кода React).

## Фаза 1: Декомпозиция кодовой базы и выделение Shared Core (Неделя 1)
*Цель: устранить дублирование кода и подготовить фундамент для параллельного WebRTC-транспорта без нарушения работы телефонии.*

- [x] **1.1. Проектирование структуры пакета `core/`:**
  - `core/config.py` — общие переменные окружения, лимиты, системные константы и цены токенов.
  - `core/audio.py` — `AudioMixer`, `UserAudioCatcher`, `AIAudioCatcher`, линейный ресемплинг 16кГц $\leftrightarrow$ 24кГц и защита от клиппинга.
  - `core/db.py` — асинхронные клиенты Supabase и Redis (`get_client_data`, `upload_audio_to_supabase`, `sb_rpc`, кэширование персоны).
  - `core/tools.py` — серверная логика и вызовы n8n для `save_lead`, `Booking_tool`, `send_sms`, `end_call`.
  - `core/archivist.py` — пост-обработка, генерация саммари через `gemini-3.8-flash`, обновление памяти клиента и отправка `post-call-summary` в n8n.
  - `core/persona.py` — сборка 10-факторного психологического портрета и правил телефонии.
- [x] **1.2. Рефакторинг `main.py` под импорт Shared Core:**
  - Перевод GSM/AudioSocket и текущего `/ws` на импорты из `core/`.
  - Сохранение `RawPCMFrameSerializer` и существующего пайплайна без изменений логики.
- [x] **1.3. Верификация регресса:**
  - Тестирование входящих/исходящих GSM-вызовов через Asterisk AudioSocket (порт 8085).
  - Проверка доставки вебхуков в n8n и записей в Supabase.

**Критерий готовности Фазы 1:** Выполнено. Модульная архитектура бэкенда; 100% сохранение стабильности текущих каналов GSM и Telegram.

## Фаза 2: Поднятие изолированного WebRTC + RTVI контура (Неделя 2)
*Цель: создать серверный канал связи с браузером с задержкой <300 мс, аппаратным эхоподавлением (AEC) и синхронной передачей UI-команд.*

- [ ] **2.1. Инициализация WebRTC эндпоинта:**
  - Реализация сигнального эндпоинта (SDP offer/answer) на базе `SmallWebRTCTransport` (библиотека `aiortc`) с поддержкой trickle ICE.
  - Настройка прямого P2P-стриминга аудио без промежуточных серверов.
- [ ] **2.2. Интеграция протокола RTVI:**
  - Включение `RTVIProcessor` и `RTVIObserver` в новый пайплайн.
  - Настройка безопасности передачи метаданных через `RTVIFunctionCallReportLevel`:
    - `control_website_ui`: `FULL` (полный пейлоад для браузера);
    - `Booking_tool`: `ARGUMENTS`;
    - Сервисные/внутренние тулы: `NAME` или скрыты.
- [ ] **2.3. Реализация серверного инструмента `control_website_ui`:**
  - Декларация схемы инструмента: `section` (enum: hero, services, pricing, cases, booking_widget, contacts, roi_calculator), `highlight_element`, `prefill_data`.
  - Обработчик `process_control_website_ui` с постановкой в очередь фрейма `RTVIUICommandFrame(command="navigate_and_render", payload=...)`.
- [ ] **2.4. Прием обратных событий от интерфейса:**
  - Обработчик `@rtvi.event_handler("on_client_message")` для приема `ui_user_interaction`.
  - Трансляция действий пользователя на экране в `SYSTEM UI EVENT` внутри `LLMContext` с вызовом `LLMRunFrame`.
- [ ] **2.5. Протокол UI Worker (v1):**
  - Подключение `UIWorker` для приема слепков доступности страницы (`ui-snapshot`).
  - Серверные команды DOM-манипуляций (`scroll_to`, `highlight`, `set_input_value`, `click`).
- [ ] **2.6. Оптимизация промпта и сессий:**
  - Сокращение системной инструкции до <200 строк во избежание сбоев `sessionResumption` в Gemini Live.
  - Реализация мягкого триггера на 110-й секунде (вместо жесткого `EndFrame()` на 120-й) с отправкой UI-команды вывода конверсионной карточки.

**Критерий готовности Фазы 2:** Серверный WebRTC+RTVI контур, синхронно передающий голос и UI-команды с задержкой <300 мс.

## Фаза 3: Серверная логика креативных механик GenUI (Неделя 3)
*Цель: реализовать бэкенд-обработчики и протоколы для 5 инновационных паттернов взаимодействия.*

- [ ] **3.1. Паттерн «Анти-Диктовка» (Voice + Micro-Form Injection):**
  - Серверная логика перевода `Booking_tool` в режим ожидания клиентского события вместо диктовки телефона по буквам.
  - Прием валидированных данных формы из браузера через `sendClientMessage` и мгновенное подтверждение в Google Calendar.
- [ ] **3.2. Проактивное чтение языка тела (Zero-Click Dwell & Selection Sensing):**
  - Обработка входящих событий долгого фокуса (>4 сек на блоке) и выделения текста.
  - Инъекция невербального контекста в LLM для проактивного предложения помощи по выбранному блоку.
- [ ] **3.3. Серверный расчет для со-симулятора окупаемости (Interactive Voice Co-Calculator):**
  - Инструмент генерации параметров расчета ROI на основе ниши и входящего трафика клиента.
  - Синхронизация подсветки ключевых метрик с речью ассистента.
- [ ] **3.4. Мультимодальный аудит экрана (Live Screen Audit):**
  - Поддержка приема видеотрека демонстрации экрана через `maybe_capture_participant_screen()` в `SmallWebRTCTransport`.
  - Передача видеофреймов в Gemini Live для проведения экспресс-аудита воронки клиента.
- [ ] **3.5. Эмоционально-реактивная морфология (Real-Time Sentiment UI Morphing):**
  - Реалтайм-анализ акустических маркеров сомнения/возражений.
  - Автоматическая отправка команды вывода видео-кейсов и гарантий безопасности.

**Критерий готовности Фазы 3:** Полный набор серверных API-контрактов, схем данных и обработчиков для расширенного взаимодействия с интерфейсом.
